# RIV-005 — Restricting effects versus verifying outcomes

Frozen pre-execution protocol. Exploratory, AI-assisted; no independent replication or production security claim.

Question: can a minimal transaction broker reduce invalid commits compared with post-hoc exact snapshot checking under an explicit restricted interface? Not a product benchmark. RIV-004 results remain unchanged.

Use Python stdlib sqlite3 on fresh temporary DB per method/case. Initial target=(0,old), neighbor=(0,clean), outside=clean. Requested exactly one write target=new. A trusted broker accepts an ordered list of proposed operations; validates the entire list against a single allowed operation; starts BEGIN IMMEDIATE, checks initial rows and outside value, executes a parameterized update, commits, and checks final rows in the same transaction before commit. All invalid plans rejected without writes; malformed inputs rejected. This is a reference prototype with caller-visible complete plans, no claim of arbitrary actor confinement. In the matched baseline, a trusted fixture executor applies proposed operations, then checks initial/final scoped rows and revision vector, as in RIV-004, not its actual product code. Use the same 12 histories from RIV-004 (including lost acknowledgement and precondition mismatch), plus malformed input controls: empty string plan, wrong operation arity, unknown resource, boolean value. Exclude malformed plans from matched baseline metrics and report separately.

Primary truth: only a clean or lost_ack proposed exact single write with initial precondition is authorized. Metrics: accepted valid/2, accepted invalid/10, invalid operations committed/10, abstentions, final database invariants and all case-level outcomes; a rejected invalid proposal that causes no committed effect is prevention, not detection. Baseline precondition mismatch blocks actor. Lost acknowledgement modeled after commit in both methods; broker re-observes committed state, does not infer actor attribution. Negative controls: bypass broker via unrestricted writer after correct commit, including outside-scope and restoring a counter; post-commit unauthorized effect may escape broker. Test failure injected after update before commit, ensure rollback and no acceptance. Report no claim that a plan validator can prevent unmediated effects. H1 broker accepts 2/2 valid and 0/10 invalid proposals with no invalid commits; H2 baseline accepts 3/10 invalid histories; H3 malformed inputs rejected without changes; H4 bypass controls show trusted complete mediation is necessary; H5 injected failure rolls back. Two deterministic runs, Python version, raw results, compile check; do not tune criteria after execution. No paid APIs or services.
